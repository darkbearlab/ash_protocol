## 原則

1. **戰場滿版，介面縮成四周的窄面板**。直向是上下堆疊，橫向左右有空間，改成像戰術遊戲那樣疊在畫面邊緣。
2. **鎖定目標資訊固定在右側欄**，不再是浮在戰場上的小卡，不會擋住戰場。
3. **鍵盤滑鼠與手把共用同一套版面**，只換按鍵提示，不用維護兩套介面。
4. **選單改成側邊抽屜或置中**，不再是手機的底部抽屜；開背包時左邊仍看得到戰場。
5. Steam Deck 是 1280×800，多出的 80px 只影響下方行動列與右側欄的高度，版面不用重做。

## 成本與規劃（2026-09-18 評估，使用者說「確實很酷，會想做，雖然不是馬上」）

### 決定成本的三件事

- **版面是為 480px 直向欄寫的**（`expansion.css` 的 `.workspace{max-width:480px}`，尺寸由 `fitLayout()` 算 `--board-size`）。桌機上現在就是一根手機柱子，所以橫向是**第二套版面**，不是調整。
- **已經有的資產讓它變便宜**：
  - 熱鍵系統（3.121.0）已有 18 個可改鍵的指令，含技能、地圖、鏡頭置中、縮放；
  - 按鈕與鍵盤都走 `data-action` → `HOTKEY_RUN` 同一條路，新版面直接繼承；
  - 所有選單是同一個 `<dialog>` 灌 HTML，抽屜化與置中卡片大多是 CSS；
  - 規則與演出早就分離，整件事不動規則層，沒有 identity 或存檔風險。
- **最麻煩的一塊是目標卡**：現在由 `src/renderer.js` 的 `placeTargetCard()` 與 `src/target-card.js` 的 `targetCardPlacement()` 在戰場上算浮動位置。橫向要改成固定右欄，這段要分支，另外新增敵人清單與紀錄條兩個面板。

### 分階段

| 階段 | 內容 | 規模 | 風險 |
| --- | --- | --- | --- |
| P1 橫向骨架 | 戰場滿版、右側欄（鎖定目標／敵人清單／最近紀錄）、上方狀態列、下方行動列、背包右抽屜、升級置中、標題畫面 | 1 個版本：新增 landscape.css 約 250 行、控制器約 150 行、目標卡與鏡頭約 80 行 | 中：鏡頭框取與版面尺寸要重算；手機直向不能壞 |
| P2 滑鼠 | 停在敵人上顯示命中率小卡、右鍵直接開火、滾輪縮放、游標提示 | 0.5–1 個版本，約 120 行 | 低：點擊命中測試已經存在 |
| P3 鍵盤補完 | 1／2／3 換武器、L 展開紀錄、選單內方向鍵導覽 | 0.5 個版本，約 80 行 | 低 |
| P4 手把 | Gamepad 輪詢、選單焦點模型、按住 Y 的道具輪盤、LT 游標查看 | 2 個版本，約 500 行與新 UI | 高：選單目前完全沒有焦點導覽；瀏覽器測不了手把，需要實機 |
| P5 Steam | Electron + steamworks.js、雲端存檔／成就／排行榜 | 獨立軌道，與版面無關 | 高，但可延後 |

P1–P3 就是完整的鍵鼠電腦版（三個版本）；加手把再兩個。

### 真正的長期成本：維護稅

之後每改一次 UI 都要看兩套版面。開工時先定死：

- **同一份 DOM**，差異盡量只放 CSS；
- **JS 分支集中在三處**：目標卡、鏡頭、滾輪；
- QA 流程加一條「兩種版面各截一張圖」。

### 零成本的預防（現在就該做）

在還沒開工前，新做的 UI 一律寫成橫向友善：不要假設 480px 欄寬、不要再往戰場上疊新的浮動元素。這樣 P1 不用回頭改前面幾版的東西。

### 排程建議

先把難度表與規則調整做完，版面大改放在規則穩定之後——否則右側欄要顯示什麼（敵人意圖、壓制層數、精英詞條）會跟著規則一直變。

### 待決定

- 橫向是依螢幕自動切換，還是設定裡手動切？（建議：偵測自動，設定可強制）
- 手機橫向要不要也吃這套？（建議只給平板以上的寬度，手機橫向太扁）
- 手把要不要在瀏覽器就支援？（Gamepad API 可以，不需要 Electron）

## 真的要做時

- 瀏覽器內的電腦版就能用這套版面；上 Steam 則要包成執行檔（例如 Electron 加 steamworks.js），才能用雲端存檔、成就、排行榜、手把支援等 Steamworks 功能。
- 橫向要另寫一套版面規則；目前的排版是為直向手機設計。
- 新增的按鍵要避開既有的：目前 Q 是瞄準資訊、Tab 是切換目標。
- 手把輪盤與游標查看是新的互動，需要設計焦點移動規則（選單內的手把導覽目前完全沒有）。

# 地圖骨架 v2（規格草案，2026-09-12，交給 Codex）

目標：讓樓層骨架**可以變形**——房間數不再固定九間、可以有大空間、邊緣可以有月台／碼頭／陽台、房間之間可以有多個連接口、敵人與物件的放置改成有預算與槽位。這份是設計規格，數值一律待定（使用者已明確說平衡之後再調）。

**不在這一版範圍內**：房間內部的細部裝飾模板池、編輯器。使用者決定先讓 Codex 把結構定下來，真的有需要再做編輯器。道具內容本身見 [ITEMS.md](ITEMS.md)。

## 現況（`src/world.js` 的 `generate`）

寫死的部分，改動時會碰到：

- 27×27 格（`SIZE`），九個房間排成 3×3，間距固定 8：`x = rx*8+2`，寬高各 `6 + rng()*2`。
- 鄰接用索引算術：`neighbors(i)` 靠 `i%3`／`i>=3`；走廊開鑿用 `Math.floor(ai/3)===Math.floor(bi/3)` 判斷同排或同列。
- 連線＝隨機生成樹＋最多兩個迴圈（`links.length>=10` 為上限）。**任兩間房之間只有一條走廊。**
- 敵人：除起點房外每間房 `3 + extraEnemies(floor) + (深層 45% 再 +1)` 隻，站位取自寫死的 `posts`（四個角，第 7 層以後補三個）。
- 物件：掩體固定在 `r.x+1, r.y+2`，油桶在 `i%3===1` 的房間右下，終端在右上角，物品位置是 `i%2`、`i===1||i===6` 這類索引算術。
- 門：整層最多 3 扇（`map.barriers.length>=3`），每間房最多一扇，開在走廊入口。
- 2×2 隔間：整層只有一個，且是由左上往右下掃到第一個合法位置就停（`placed` 旗標），所以位置偏上偏左。
- 每間房抽一個 `r.kind`（貨架倉庫／環形機房／錯列檢查點），對應 `shapes` 裡四格相對中心的牆。
- 房間編輯後有連通性驗證：破壞可達性就整組回退成空房。**這個安全網要保留並延伸到所有新機制。**

## 1. 格位與房間分離（核心，其他全部依賴它）

把「第 i 個格位」和「第 i 間房」拆成兩層：

- `cells[9]`：每個格位記它屬於哪一間房的 id。
- `rooms[]`：每間房記它佔哪些格位，矩形取聯集。

規則：

- 連線仍在**格位**上計算（生成樹＋迴圈不變），算完後**同屬一間房的連線直接移除**，因為內部本來就通。
- `mainRoute`／`rewardRooms`／`startRoom`／`endRoom` 仍以房間 id 表示，下游邏輯不用改。
- 起點房與終點房不得合併（避免一個大廳同時是起點與終點）。
- 合併只允許**正交相鄰**的格位，單間房最多 4 格；2×2 合併每層最多一間。

## 2. 合併房與大空間

- 雙格合併＝14×6 或 6×14 的長廳（停機坪、車間、月台大廳）。
- 合併房的房型模板應該是「開放式」：不畫內牆，改放中央大型物件群（例如停機坪中央的機體）。
- **射程後果要一起考慮**：14 格長的開放空間超過多數武器射程，會變成狙擊與接近戰的空間，霰彈與近戰職業在那裡吃虧。因此合併房的敵人配置不該沿用一般房間的配池（見第 5 節），煙霧、暗區、掩體在這種空間的價值會顯著上升。

## 3. 邊緣附屬區（陽台／月台／碼頭）

- 房間在 x = 2 / 10 / 18，寬高各 6～7，所以**地圖最外圈本來就空著**。**邊緣格位是八個**（3×3 去掉中央），角格有兩個外側、邊格有一個。**可用寬度不一致**：左側與上側固定 2 格，右側與下側則視該房寬高為 6 或 7 而有 2～3 格。附屬區必須**實際計算可用範圍**，不能假設四邊相同，**但不需要改 `SIZE`**。
- 外側就是地圖邊界，本來就不可通行，**懸空感是免費的**，不必另做虛空格。
- 房間與附屬區之間用 `low_partition`（矮隔板）當欄杆：現有定義是**擋移動、不擋視線、不擋射擊、可翻越**，正好是欄杆。開口另外留 1～2 格。
- 效果是一條沒有掩體的側翼路線：看得到、打得到、要過去得花動作，並且天然形成一個迴圈。
- 外觀換 `themes.js` 的地板 role 即可（純外觀，零風險）。附屬區種類先定三種：月台、碼頭、陽台。

## 4. 連接口與門（使用者追加）

現況是任兩間房之間只有一條走廊，整層最多三扇門、每房一扇。改成：

- **每條房間連線可以有 1～3 個連接口**，數量由骨架配方或房型決定，不是全域統一。合併房的邊比較長，允許的上限也比較高。
- 連接口之間至少隔 2 格，避免變成一整面開口。
- **每個連接口獨立決定有沒有門**，門的比例由配方給（例如「這層的門比例偏高」＝實驗室主題）。**同一條連線不得所有連接口都有門**，至少留一個空口，避免整間房被門封住。
- 門的全域上限從 3 放寬，改成依連接口總數的比例，並保留「門是可開關、會擋視線、可破壞」的既有規則。
- 注意：多開口會**削弱卡口戰術、讓敵人更容易繞後**，也會增加視線。這是想要的變化，但應該是**主題差異**（倉庫多開口、實驗室多門）而不是全圖統一。
- `createLighting` 吃 `corridorPaths`，走廊變多會影響暗區分布，要一起看。

## 5. 生成預算與分級哨位（使用者追加）

把「每間房 3 隻」換成**每層的威脅點數預算**：

- 每個敵人類型有點數成本；一層的預算依**面積與樓層**計算，分配到各房間（起點房除外）。合併房面積大、拿到的預算也多。
- **哨位改成由房間輪廓算出來**，不再是寫死的四個角。現在 `posts[j]` 取超過陣列長度會生出座標 `undefined` 的敵人，合併房與附屬區一定會踩到，必須先改。
- **哨位分級**：主哨位（有掩體、朝向入口）、次哨位、**巢穴錨點**。

### 巢穴：蟲群改成執行期逐隻出現（2026-09-12 使用者決定）

不在生成時一次放下整群，改成放一個**巢穴**（可破壞的物件），玩家進入觸發半徑後**每回合／每 k 回合放出一隻**。這個做法比一次生成好在三點：

1. **從根本上避開壞資料與塞爆空間**：出生點是執行期從巢穴周圍的空格算出來的，不再依賴生成時的固定哨位陣列。
2. **上限改成「同時存活數」**，而那正是真正的成本（尋路與演出），總量反而可以放寬。
3. **巢穴本身變成目標**：給玩家「往前推掉它」的理由，也支援「不必殺光也能過」的方向。

現成的先例：頭目／封鎖官在半血時會即時生成無人機（`game.js` 的 `e.reinforced` 分支），撤退增援（`game.reinforcements`，save v21 就有）也是執行期到場。**所以先後手佇列、id 配發與存檔都已經處理過敵人中途出現這件事。**

約束：

- **觸發後就保持啟動**，不能靠走出半徑再走回來重置，否則變成原地補血再刷。
- 每個巢穴有**有限的總產出**；破壞巢穴即停止。
- **不給掉落**：`game.js:456` 的 `if(e.reinforcement)return;` 已經在戰利品、彈藥與護甲板之前提早返回，蟲群可沿用這個旗標擋物品掉落，但仍須加上 5.1 的獨立 `expendable` 旗標，才能同時擋經驗與廢料；不要改掉撤退增援的既有收益。**否則裝甲回收升級配上會持續產出的巢穴等於無限護甲板。**

## 5.1 零經驗要先修兩個現有問題

使用者決定蟲群與雜兵**經驗極少或完全不給**。照現在的程式碼做不到：

1. **經驗是在提早返回之前發的**：`game.js:446` 的 `this.player.kills++; this.player.xp+=...` 在 456 行的 `if(e.reinforcement)return;` **之前**，所以現在的增援其實照常給滿經驗。
2. **廢料也一樣**：`game.js:447` 的 `this.player.scrap += ...`（含拾荒加成與工程師的擊殺廢料）同樣在提早返回之前。
3. **`ENEMY_TYPES[e.type]?.xp||1` 用的是 `||`**，所以在資料裡寫 `xp:0` 會**退回 1 點**，不是 0。要改成 `??` 才能真的設成零。

**但不要順手把撤退增援的獎勵一起拿掉。** 撤退增援是原路回收任務的壓力來源，它現在給的經驗與廢料是那個任務經濟的一部分；一起改等於悄悄削弱一整個合約，而使用者已經明確說這一輪不動平衡。建議**替新單位另開旗標**（巢穴子代與雜兵），零經驗、零廢料、零掉落只套用在新旗標上，`reinforcement` 的語意維持不變。這樣既有的撤退測試也能留著當回歸驗證，而不是改掉斷言去迎合新行為。

## 5.2 雜兵（DOOM 2016 式的殭屍，2026-09-12 使用者提案）

幾乎沒有威脅、很慢、會擋路、偶爾舔一口血的填充單位。可以做，但**要用它對玩家的成本來定義，而不是用它的威脅來定義**：在 DOOM 裡殺一隻花半秒，**在這裡殺一隻花一整個回合**，所以「沒威脅」不等於「免費」，它是對回合與彈藥的稅。

- **「慢」要另外定義**。`traits.js` 的緩速是**階段排序**（`initiative` 回傳 -1／0／1），代表在普通階段之後行動，**仍然每回合行動一次**，不是兩回合一次。所以緩速不會減少演出成本，也不能為了雜兵改掉它的既有意義；要隔回合行動得另立一條行動間隔規則。**結論：同時存活數上限是演出時間唯一的槓桿**，要保守設定。
- **擋路的解法改用全職業徒手近戰**（見 5.4），不另立「推開」規則。原本考慮過比照 3.38 移除的友軍推動做一條推退規則，但徒手近戰同時解決擋路與清理，一個機制取代兩個。
- **不掉落、不給經驗**（同 5.1）。
- 傷害設計成**懲罰原地不動**的削血，貼著才會被舔到；`crawler` 的「拉開一格即可避開攻擊」已經是這個模型。
- **任務目標資格要明確排除**。合約裡沒有「清空全場」，但 `missions.js:32` 挑 hunt／sweep 目標時**只排除 boss 與 warden**，所以雜兵會被選中。必須依類型或旗標排除。
- **連帶的失敗模式**：目標湊不齊時 `prepareMission` 會丟出「無法配置任務目標」。`sweep` 需要三個分布在不同房間的合格目標，而合併房會讓房間變少、雜兵會讓合格者變少，兩件事同時發生就會擲出例外。**威脅預算必須保證足夠數量的非雜兵敵人分布在足夠多的房間**，這是預算公式的硬性輸入，不是事後檢查。
- **和蟲群是同一個設計欄位，要分化**：巢穴放**快而弱**的（必須回應的壓力），手放的雜兵是**慢而弱**的（繞過去就好的障礙）。否則每層都只是「一堆弱東西」。
- **要觀察的風險**：必須被射擊的雜兵會悄悄削弱槍械 build、變相加強近戰。近戰職業目前偏吃力，所以這也許是好事，但影響面很廣，列為觀察項，不在這一版調。

- 敵人 id 目前是 `${floor}-${i}-${j}`，群聚要保證唯一；`floorStates`（原路回收）以此為鍵。

## 6. 放置槽位：寶箱、油桶、模組（使用者追加）

把「索引算術決定位置」換成**槽位系統**：房間產生一組候選槽位（依輪廓與模板），再由各系統依優先序去取。

- **必要物件先取**（終端、任務目標、保底武器），其次補給箱，最後是裝飾與可選物件。
- **油桶不再固定在角落**，改成可放在任何合法槽位；它是可破壞且會爆炸的物件，放在通道旁比放在角落有趣得多。既有規則（不得落在走廊格）保留。
- **2×2 隔間／生活模組不再限一個、也不再固定偏中央**：掃描順序改成隨機，允許一層多個，`addLivingModules` 已經支援旋轉與驗證，沿用即可。
- **預留「隨機寶箱」槽位**：`containers.js` 的 `CONTAINER_KINDS` 已經是現成的容器機制（可走上去、開啟一次、內容掉到地上）。新增一種「未識別貨櫃」，內容由掉落表決定，用來裝**道具與技能**那類非目前消耗品的東西。內容先留空表，等 [ITEMS.md](ITEMS.md) 的第一批道具定案再填。這一版只要**保證槽位存在且會被生成**。
  - 建議每層 0～2 個，偏好放在支線房（`rewardRooms` 之外的葉節點），讓探索有回報。

## 7. 骨架配方（可貼上的 JSON）

使用者要的「複製一份 JSON 加進池子」指的就是這一層：

```json
{
  "id": "dock-row",
  "name": "碼頭側線",
  "theme": "dock",
  "floors": [3, 99],
  "weight": 2,
  "layout": [["A", "A", "B"],
             ["C", "D", "E"],
             ["F", "G", "G"]],
  "annex":   { "A": "platform-north", "F": "dock-west" },
  "openings": { "default": [1, 2], "A-B": [2, 3] },
  "doorRatio": 0.3
}
```

- `layout` 用字母標示格位歸屬，**相同字母＝合併成同一間房**。
- `annex` 只能掛在邊緣格位上；驗證時要拒絕掛在中央格。
- 未提供的欄位吃預設值；配方池為空時要能退回現在的 3×3 行為（作為 v1 相容基準與測試基線）。

## 8. 不變條件（每一項都要有測試）

1. 起點、終點、所有敵人、所有物品、所有容器**必須可達**（既有的 `reachable` 檢查，含門視為可開）。
2. 沒有孤立的地板格：`reachable({props:[]})` 的大小要等於地板總數。
3. 走廊格上不得有實體 prop 或危險格（既有規則）。
4. 每間房至少一個連接口；同一條連線不得所有連接口都有門。
5. 起點房不生成敵人。**注意：這不是既有規則**——`world.js:100` 現在會 `unshift` 一名步槍兵斥候到起點房。v2 遵守本條，把這個額度移到其他房間；空配方的 v1 相容模式保留舊行為並保留對應的相容測試。
6. 附屬區必須與母房相連，且不得成為唯一的主線通路。
7. 每層實際敵人數不超過上限；每層威脅點數落在預算容差內。
8. 生成是**純函式**：同 `seed`／`floor`／`unlocks` 產生完全相同的地圖。

## 9. 會被影響的東西

- **存檔不用升版**：`serialize()` 直接 dump 整個 game（含 `grid`、`rooms`、`props`），地圖是存下來的、不是重生的。所以改生成器只影響新生成的樓層，舊局照舊。
- **每日種子的紀錄會失去可比性**：RNG 抽取次數一改，同一個種子就不再產生同一張地圖。`src/daily.js` 的排行或紀錄若有跨版本比較的意味，要標記世代。
- **既有 fixtures**：`qa/create-*.mjs` 產生的場景檔綁著舊地圖，重生前要先確認哪些測試依賴具體座標。
- **演出時間**：敵人數上限直接決定每回合等待時間，這是手機體感的主要來源之一。

## 10. 分期

1. **格位→房間的間接層**＋面積化的威脅預算＋輪廓化的哨位。不加任何新內容，但它是後面全部的前提。
2. **合併房**與開放式大空間。
3. **多連接口與門比例**。
4. **邊緣附屬區**（月台／碼頭／陽台）＋ themes 地板。
5. **槽位系統**：油桶自由放置、多個生活模組、預留隨機寶箱。
6. **骨架配方池**與主題綁定；這時候使用者就能直接提供 JSON。

每一階段都應該能單獨上線並通過既有測試；配方池為空時退回現行行為。

## 11. 待 Codex 決定

- 合併房的最大格數（建議 2，2×2 每層最多一間）。
- 威脅點數的分配公式要不要沿用 `ENDLESS_TUNING` 的成長曲線，還是另立一條。
- 群聚單位進先後手佇列的方式：逐隻排、還是整群共用一個順位（後者對演出時間友善很多，但會改變先後手規則，是規則層的決定）。
- 附屬區要不要參與 `mainRoute` 計算（建議不要，只當支線與迴圈）。

## 5.3 雜兵擊殺回饋：追擊（2026-09-12 使用者提案，Claude 修正實作形狀）

**設計**：玩家親手擊殺雜兵（含巢穴子代）不消耗回合。**只有玩家本人的傷害算數，召喚物、寵物、機體的擊殺不算**——否則死靈法師／德魯伊／工程師可以用友軍的攻擊無限延續。

這個設計把雜兵從「回合稅」變成「資源」：槍械職業付的是子彈，近戰職業則因為戰意、嗜血、伏擊都吃位置與擊殺，可以把雜兵當成延續增益的中繼跳板，等於實質加強近戰。

**實作不要用「跳過剩下的行動」。** 原因在 `game.js:246`：玩家、敵人與友軍是**同一條依速度排序的佇列**（`initiativeQueue` → `queue.sort(...)` → 253 行依序執行），所以**快速敵人會在玩家的攻擊結算之前就行動**。等到知道雜兵死了才中止後續，會留下半推進的世界：快速的動了、普通與緩速的沒動，而回合數又沒有增加；下一次輸入重建佇列時，快速單位就會在緩速單位動一次的期間動兩次。蓄勢、煙霧到期、轟炸標記、中毒與失能計數也都掛在回合推進上，半個回合會讓它們全部失準。

**正確的形狀已經在程式裡了：忍者影步。**

- `game.js:411` 觸發時設定 `this.shadowSteps`，並寫入訊息。
- `game.js:225` 在**付費路徑之前**攔截，`shadowMove` 完全不進佇列。
- `game.js:419` 移動、遞減、撿拾、更新視野，**不推進回合**。
- `game.js:226` 做任何不合格的行動就放棄剩餘步數。
- `game.js:47` 與 `707` 在換層與撤離時歸零。

**建議：雜兵擊殺改為授予一枚「追擊」代幣，完全比照影步實作**——攔在付費路徑之前、不碰佇列、不動先後手規則。與使用者原案的差別只有一個：**第一次擊殺仍然付一個回合，之後的連鎖才免費**。這反而更好——進入連鎖有成本，維持連鎖靠技術；而且它不需要動規則層任何一行。

要釘死的規則：

- **一次行動最多授予一枚，不疊加**。否則一顆破片炸死五隻雜兵就等於五次免費行動，投擲物會變成無限回合機器。
- **不合格的行動即放棄**（照抄 `game.js:226`）。
- **與影步不疊加**：`shadowSteps>0` 期間擊殺雜兵不授予代幣，否則忍者會得到「伏擊→影步→殺雜兵→新代幣」的永動機。
- **巢穴的冷卻以付費回合計算**，所以連鎖期間巢穴不會產出，玩家不可能被連鎖反噬，也不會被巢穴追上。這條自洽，不需要額外防護。
- 換層、撤離、失能時歸零；存檔多一個整數欄位，與 `shadowSteps` 同級。
- 遠程擊殺**也給**代幣。近戰的優勢會自然浮現（戰意／嗜血／伏擊都要貼身），不需要為了強調近戰身分而多開一條特例。

**待觀察（不在這一版調）**：這讓遠程清雜兵的唯一成本變成彈藥，等於把雜兵密度變成一個彈藥消耗的旋鈕，影響所有槍械 build。

## 5.4 全職業徒手近戰（2026-09-12 使用者定案）

**現況**：`game.js:166` 的 `bumpMeleeSlot()` 是去 `player.owned` 裡找一把近戰武器，而且要求切換來回都免費。所以**八個職業裡有五個不能近戰**，撞上去只會得到一則失敗訊息。

**決定**：所有職業都有徒手近戰。理由不是風味，是**追擊（5.3）沒有它就只寫給三個職業**——免彈藥清雜兵的手段目前只有重裝兵、狂戰士、忍者有，其餘五個每殺一隻雜兵都要付子彈。另外，彈藥見底加上一隻雜兵卡在單寬走廊，現在是真的走不過去。

**實作形狀：虛擬回退，不要真的加一把武器。**

- `bumpMeleeSlot()` 找不到合格近戰武器時回傳一個哨兵值，`weaponAt` 對該哨兵回傳徒手側寫。
- **呼叫點只有三個**：`game.js:191`（驗證）、`232`（執行）、`420`（影步三階的追加近戰）。
- 徒手**不進 `player.owned`**，所以背包分頁、`PACK_LIMIT`、地面武器交換、拆解、改裝、切換循環全部不受影響，也不需要「不能拆／不能改／不能丟」這類特例。存檔驗證只要接受哨兵值。
- 它也繞過了「切換要免費」那個條件——徒手沒有東西要切換。

**規則**：

1. **傷害只夠處理雜兵**。徒手應該一擊解決雜兵，對步槍兵幾乎沒有意義。忍刀是 30～36，徒手要明顯低於它。近戰職業是**付了一個背包格**換那把武器的，這個差距要守住。
2. **不做誤觸保護**（使用者定案）。撞到誰就打誰，跟現在持近戰武器的職業行為一致；拿拳頭打重裝敵人而浪費一回合是玩家的判斷問題，不另立「只對雜兵自動觸發」的特例。少一條規則。
3. **近戰專屬效果不得繼承**。`bladeMultiplier`、`meleeReward`、伏擊倍率都是讀 `weapon.melee`；虛擬徒手若標 `melee:true` 會一併吃到，忍者空手伏擊會變成 1.95 倍。必須明確排除。
4. **徒手擊殺雜兵照樣給追擊代幣**（5.3）。這是整套設計成立的關鍵。

**附帶好處**：通用升級「格鬥訓練」（三階，`meleeAccuracy`／`meleeEvasion`）已經存在，但現在只對三個職業有意義；徒手一開，它立刻變成全職業有用的選項。

## 12. 2026-09-12 修訂（對照 Codex 的實作規劃）

Codex 讀過本規格後提出的落差，已逐項在程式碼中確認並改寫上文：起點房的斥候（第 8 節第 5 條）、緩速的真實語意（5.2）、邊緣格位是八個且寬度不一（第 3 節）、增援同時拿經驗與廢料（5.1）、任務目標只排除頭目（5.2）。另外補充三點：

- **`FLOOR_FIELDS` 是固定清單**。`retreat.js` 的 `archiveFloor` 只 `structuredClone` 該清單列出的鍵，漏掉不會報錯、只會**靜默消失**。新增的 `cells`、`openings`、`annexes`、`generation` 與巢穴狀態都必須加進去，並補一條「封存後返回仍保有 v2 欄位」的測試。
- **門的比例取決於連接口數量**。既然「同一條連線至少留一個無門通道」，只有單一連接口的連線就永遠不能有門。若第 3 階段沒有保證部分連線拿到兩個以上的開口，整層的門會比現在**更少**。配方應該能對「想要門」的連線要求至少兩個開口，而門比例要在開口數決定之後才評估。
- **同時存活上限要涵蓋所有來源**。巢穴子代、撤退增援與頭目半血增援會疊加；上限若只算巢穴，原路回收的回程會同時吃到兩種增援而爆掉。

另外，5.3（追擊代幣）與 5.4（全職業徒手近戰）是使用者 2026-09-12 的定案，與巢穴、雜兵同屬第 5 階段之後的執行期批次。

Codex 規劃中被採納的四個判斷：合併上限 2 格（2×2 每層一間、入口出口單格；硬限制為三個不同房間有合格任務目標，不以總房間數取代）、威脅預算不把生命與攻擊的成長乘進數量、蟲群**逐隻排入既有佇列**（規則層維持逐隻成立，演出合併由 Claude 在表現層處理）、附屬區不參與 `mainRoute`。

- `openings[].cells` 保存房間界面間的完整走廊區域（含彎道小支段），`path` 是區域內依序相鄰的通路，`mouths` 為兩端入口，順序對應 `rooms`。分開保存是因為第一階段的 cells 是多段挖掘路徑聯集，未必是一條有序路徑。
- `barrierIds` 記錄 path 上的門，仍是生成時參照，破門後可能不再有相應活門；不能因這種正常遊玩狀態拒絕讀檔。保存驗證檢查入口歸屬、通路相鄰與區域包含、連線對應、數量及至少一條空口。
- `generation={version:4,recipeId,skeleton}`；skeleton 記錄實際下層骨架 `grid-v2`／`long-halls-v3`／`hangar-v3`。`MAP_GENERATION=4` 為可讀上限，歷史及混合局採實際世代集合，例如 `[3,4]`，不強行把回退地圖記成 4。
- save v32、profile v5、backup v1 不變；openings／generation 已在 FLOOR_FIELDS，新增內容隨原欄位完整保存。已存的世代 1～3 樓層維持舊門和原地圖，不重新生成。
